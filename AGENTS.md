# CorniSand — agent guide

Falling-sand sandbox running entirely on the GPU: WGSL compute shaders run a Margolus cellular automaton over storage buffers (sand, liquids, gases and fire by local rules), and a fullscreen-triangle render pass draws the result. TypeScript, Vite, native WebGPU, no framework.

## Commands

```bash
npm run dev       # Vite dev server
npm run build     # tsc --noEmit, then production build → dist/
npm run typecheck # tsc --noEmit (strict; covers src, tests, vite.config.ts)
npm run lint      # ESLint (typescript-eslint, type-aware)
npm test          # Vitest
npm run preview   # Serve dist/
npm run bench     # GPU time per frame (timestamp queries) at 2560×1340 at 1x to 8x for `tank`, `mix75`, `full100`, `blast`, `thermal` (heat everywhere) and `pot` (a screen-wide tank heated from below, convecting), the 1x time of each pass, the renderer's passes (`render:coverage`, `render:glow`, `render:shadow`, `render:composite`, summed in the `render` column) in the finished and the cells look, and the simulation creation time (tests/bench.gpu.ts); needs a GPU adapter. BENCH_SCENES=mix75,blast and BENCH_SPLIT_ONLY=1 narrow it; BENCH_AIR=off,8,4,2,1 runs it at each air cell size (`off` is `air: false`; default 4); BENCH_LOOKS=cells narrows it to one look
```

CI (`.github/workflows/deploy-pages.yml`) runs lint, test and build before deploying.

The GPU suites in `tests/` run the real WGSL through Dawn's Node bindings (`webgpu` package, `tests/gpu.ts`) and skip themselves when no adapter is available, as on the CI runners (`docs/backlog.md` D11). `tests/gpu.ts` must keep a module-level reference to the GPU instance: Dawn crashes the process if it is garbage-collected while its device is in use.

## Stack facts not in config

- WebGPU only, no WebGL fallback. Targets Chrome 113+, Edge 113+, Safari 18.2+.
- The reference machine is an RTX 4080. It is also the user's gaming GPU: before `npm run bench`, check with `nvidia-smi` that nothing else loads it (a game or a live wallpaper once made a bench run 3 to 8 times too high); ask the user to close it if it does. Every size and resolution (field, cells per pixel, air, gravity and light grids, CA steps per frame) is a setting, not a hard-coded constant, so it can be scaled down later (`docs/decisions.md`).
- `.github/workflows/deploy-pages.yml` builds and deploys to GitHub Pages on every push to `main`; `vite.config.ts` sets `base: './'` for that.
- The simulation grid is one cell per CSS pixel of the canvas, or the smallest integer cells-per-pixel scale that fits the device's storage-buffer limits (`src/grid.ts`). It is sized once at load (`src/main.ts`); resizing stretches it (see `docs/decisions.md`).
- The user's npm `min-release-age` is 7 days: `npm install` picks the newest version at least that old, not `latest`.
- TypeScript stays on 6.0.x until typescript-eslint supports 7 (`docs/backlog.md` D10).

## Layout

- `src/main.ts` — entry: WebGPU init and device re-creation, UI wiring (the Scenes menu, element and Heat/Cool tool selection, the heat view and its H key, the air view and its A key, the Wind tool, the C key (finished look or cells look), the `?air=<size>`, `?wall=<0..1>` and `?scene=` parameters, the pointer readout, speed), frame loop (one encoder, one submit per frame).
- `src/gpu.ts` — adapter/device/context setup with the adapter's buffer limits, uncaptured-error banner, device-lost callback, reload overlay.
- `src/grid.ts` — `computeGrid`: grid size and scale from the buffer limits.
- `src/simulation.ts` — compute pipelines (brush, CA, particle count); `probe`/`readProbe` copy one cell's `kind` and `temp` for the pointer readout; `simulate(encoder, supersteps, input)` records the brush pass, the air's mask, wind and exchange passes, and the CA steps with the air steps into the caller's encoder. Options: `air` (default true) and `airCellSize` (1, 2, 4 or 8, default 4).
- `src/air.ts` — `AIR`, the air's constants in grid cells and dispatches (wave speed, speed limit, losses, heat exchange, buoyancy, `push`, `matterLoss`, burst scale, Wind tool gain, view range), `PRESSURE_RAMP` and `AIR_VIEW` for the air view, `windVelocity`, `airSubsteps`, `airConstantsWGSL`.
- `src/air-grid.ts` — `AirGrid`: the air buffers (state, scratch, mask, burst), the mask, wind, exchange and per-step passes, `load`, `clear`, `read`, `probeOffset`.
- `src/readout.ts` — `formatProbe`, the pointer readout line.
- `src/passes.ts` — `PassRecorder`: the frame's one compute pass, or for the bench (`PassTimer`) one timed pass per group of dispatches.
- `src/cell-fields.ts` — `CELL_FIELDS`, the one list of per-cell fields (name, WGSL type), plus `CellData`, `FIELD_BYTES` and `tempView` (the `temp` words as floats).
- `src/physics.ts` — the grid's physical scale: `G`, `CELL_SIZE` (1.36 mm) and `DISPATCH_TIME` (2.08 ms) derived from `DEFAULT_GRAVITY`, `PAIR_TIME`, and the conversions the physical properties use: `CONVECTION_GAIN`/`convectionChance`, `REF_DEPTH`/`spreadSpeed` (viscosity), `slideSpeed` with `MAX_REPOSE`, `MIN_REPOSE` and `REPOSE_FIT` (angle of repose). A change of scale or of a property's conversion is a change here.
- `src/heat.ts` — temperature constants: `ROOM_TEMP` (what an element is painted at by default), `ABSOLUTE_ZERO`, `MAX_TEMP`, `NO_THRESHOLD`, `heatShare` (the TypeScript twin of the conduction share) and `effectiveTemp` (the TypeScript twin of `cellTemp`).
- `src/half.ts` — binary16 conversion and `packHalf2`/`unpackHalf2`, the CPU side of the packed `velocity` and `remainder` words (scenes and tests).
- `src/movement.ts` — `MOVEMENT`, the movement constants (top speed, launch speed, friction, flyer cap), `movementWGSL`, `launchGroups`.
- `src/flyers.ts` — `Flyers`: the flyer buffers and passes of a superstep (launch, flight, landing, compaction), the overlay the display reads, the brush removal, read-back helpers for tests.
- `src/cell-field-buffers.ts` — `CellFields`: one storage buffer per field, the shared bind groups (`@group(1)`), `load`, `clear`, `read(name)` for tests.
- `src/display.ts` — `Display`: records the frame's render passes (coverage, glow chain, shadow, composite; see `docs/rendering.md`) after `recordOverlay`; the composite draws the cell field buffers, the wall, the brush ring and the effects of the finished look, the heat view (each cell that holds heat in the color of its temperature, from `HEAT_RAMP`, and empty space in the color of its air's temperature) and the air view (pressure from `PRESSURE_RAMP`, wind arrows); `Display` takes `{ air?: AirGrid; settings?: Partial<LookSettings> }` as its last argument and `render` an optional `PassTimer`.
- `src/look.ts` — `Look` (`'finished' | 'cells'`), `LookSettings` and `LOOK` (every effect's strength and field size), `parseWall`.
- `src/display-table.ts` — `DISPLAY_FIELDS`, `packDisplay`, `DisplayTable`: the uniform of 256 rows of 8 words (grain, opacity, absorption, padding) that only the display and the coverage pass bind, from `ElementDef.look`.

## Invariants

- A cell is one 32-bit word in each field buffer of `CELL_FIELDS`: `kind` (bits 0–7 type, 8–15 variant, 16–31 reserved), `life`, `velocity` and `remainder` (each two binary16 values packed in a `u32`, x in the low half, in cells per dispatch; zero for anything that does not fall), and `temp` (`f32`, the stored temperature in °C; meaningless for empty space and walls). The fields are declared once in `src/cell-fields.ts`; every shader gets the `Cell` struct, its bindings (`@group(1)`, binding = field index) and the accessors (`cellType`, `cellVariant`, `cellLife`, `cellVelocity`, `cellRemainder`, `cellStoredTemp`) from `cellWGSL` in `src/shaders/cell.wgsl.ts`. Add or change a field there only; never index a field buffer by hand. A pass's own bindings (uniforms) are group 0; group 3 of the CA and the flight pass holds the launch counts and, with air, the air state (binding 1) and the burst buffer (binding 2). Every pipeline fits the default per-stage limit of 8 storage buffers that the game and the tests run at (`tests/gpu.test.ts` asserts it): the CA is at 8 (five fields and three), the flyer passes that carry whole cells bind three buffers of their own plus every field, the air exchange pass 7 (three fields, four air buffers), the display 7 (its sampled textures and sampler are separate, `docs/rendering.md`, "Bindings"). A sixth field needs backlog D32 first; the flight and retry passes bind `kind` only (`CellFields.subset`).
- Elements are rows of `ELEMENTS` in `src/elements.ts`, and no file outside it names an element ID: TypeScript uses `ELEMENT.SAND`, shaders use `EL_SAND` and `ST_POWDER` (generated), and the toolbar is built from the table. IDs fit in 8 bits, are never reused, and `EMPTY` (0) and `WALL` are required: out-of-bounds cells are walls and the brush erases to empty. The table reaches the CA, the brush and the display as a uniform array of 256 rows of 144 bytes in `@group(2)` (`ElementTable`; `PROP_FIELDS` lists the row's 36 words and generates both the WGSL struct and the packer, a multiple of four words as a uniform stride needs). Three words are padding (`pad1` to `pad3`): a new row word takes one of them, and a fourth grows the row to 160 bytes (40 words), which every row of the table pays for. `Simulation` takes another table (and extra rule sources) as options, which is how tests add rows.
- Movement depends on `state`, `density` and, for powders and liquids, the cell's velocity: they gain their element's `gravity` per dispatch, move one cell inside the block when the remainder reaches 1, and fall through empty space, gases and lighter things; a gas rises through empty space, plasma (fire) and heavier liquids; solids and plasma never move on their own. A cell faster than `MOVEMENT.launchSpeed` leaves the grid as a flyer (below). Gases ignore velocity and move by their density against the air's (phase 0, `buoyancy`): a gas rises or sinks into the empty cell above or below with the chance `convectionChance(airDensity, gasDensity)` (the square root of the relative difference times `CONVECTION_GAIN`, at most 1), where `airDensity` is `elDensityAt(EL_EMPTY, airTempAt(...))`, read once per block that holds a gas (room temperature without air); a gas rises through fire or a heavier liquid at once. With air they also drift with it (`driftCell`). With air, a powder or liquid also moves toward the air's velocity by its element's `drag` and is pushed by the air's pressure gradient over its density (`AIR.push`), in the grid and in flight. Density by temperature (`densityAt`, twin `elDensityAt`): a liquid with `densityKnots` follows them, a gas the ideal-gas law, a powder or solid has one density. Two cells of one liquid with knots, one above the other, swap with the chance `convectionChance` of their densities at `cellTemp` (`convect`, part of phase 1): that is convection, and a body at one temperature stays still. Two different elements are still ordered by their nominal densities (`canDisplace`, `canRiseThrough`): the temperature-aware compare cost the CA 15% and no pair of the table crosses over (backlog D34 before adding one that does). A liquid spreads, and slides down to a free bottom corner, only with the chance its row's `spread` word gives, `spreadSpeed` of its density and viscosity for a layer `REF_DEPTH` cells deep, capped at 1 (`viscousGo`; water is at the cap, bit-identical to no viscosity). A powder with a `repose` leaves a step it slides off with the sideways speed `slide` (`slideSpeed`), which friction stops and which sets the pile's angle; a resting grain with a one-cell step beside it does not slide. A rule that changes a cell uses `withType`/`retype`, `withLife`, `withMotion` or `withTemp`, which keep every other field; `makeCell` builds a fresh cell with motion zero and is for the brush and scenes. Ignition is decided from the cells after the lifetimes but applied after the element rules, so a rule never sees a cell that ignites in the same dispatch.
- Flyers: a cell that leaves the grid is a `Flyer` (position, velocity, the whole `Cell`) in a list of at most `maxFlyers` (`Simulation` option, default `MOVEMENT.maxFlyers`); past the cap launches stay in the CA, clamped. The flyer passes run once per superstep, after the offset-1 dispatch, inside the frame's one compute pass; every slot comes from a prefix sum and every landing conflict from a claim key, so nothing depends on thread scheduling. A flyer is blocked by any non-empty cell, flyers do not collide with each other, the air pushes a flyer in flight like a grid cell, and only the brush's erase and replace otherwise reach one. A flyer carries its temperature but exchanges no heat and changes no phase until it lands. The display draws flyers from an overlay buffer that `recordOverlay` fills after `simulate`.
- The cells are updated in place, one buffer per field, no ping-pong. A CA rule reads and writes only the cells of its own 2×2 block (that is what makes the threads race-free); `storeChanged` writes back only the fields that differ from what the block loaded. Reading a neighbor outside the block breaks in-place updates silently, and the determinism test cannot see it (two runs of one seed agree even then). `tests/block-locality.test.ts` guards it: it runs one dispatch on a random scene holding every element of the table and on a copy with one cell changed per 4×4 tile, and requires bit-identical fields outside the blocks of the changed cells. It catches a read only when it changes a result for the cells drawn: continuous phases nearly always, discrete ones with high probability over its 32 rounds, not with certainty, so still review rule changes for it. A new cell field needs a generator there (it throws on a field it does not know).
- One thread handles one 2×2 block. Out-of-bounds reads (`readCell`) return a wall cell, the world boundary; out-of-bounds writes are skipped.
- The CA keeps the block in one private variable per slot (`blk0`–`blk3`, `blkAt(k)`/`setBlk(k, c)`), never in a private array indexed by a runtime slot: such an array lives in per-thread memory and made the CA three times slower. The same holds for any new per-block state.
- The CA skips a block whose four cells are all inert (`elementInert`: empty or solid, no lifetime, no rule, and no heat: `elementHoldsHeat`, a conductivity above 0 or a transition, and no pressure transition) without loading their other fields. Anything that changes such a cell by itself must make `elementInert` false for it or run outside the CA: that is why a metal or stone cell wakes its block, and why WALL (which holds no heat) stays skippable. The skip and the launch count also rely on empty and solid cells having zero velocity: every runtime path keeps it so (`retype`, `makeCell`), and a scene loaded through `Simulation.load` must too.
- Heat: only an element that holds heat (`elementHoldsHeat`) has a temperature. EMPTY and WALL hold none, so the cell grid's heat never leaves the world by conduction (empty space has the temperature of its air cell instead, see Air); the conduction guard (`g` is 0 unless both conductivities are above 0, nothing is written when `d` is 0) keeps their `temp` words untouched, which is what keeps NaN out of them. Conduction exchanges heat by `cellTemp` (the stored temperature clamped to the element's thresholds) and changes the stored value, which may run past a threshold while a cell takes in its latent heat; only phase 8 compares the stored value. The stored value may also leave `ABSOLUTE_ZERO`..`MAX_TEMP` during a latent range (steam condensing runs about 1,130 °C under 100 °C): validation accepts it, `cellTemp`, the readout and the views stay inside the range, and the Heat and Cool tools clamp to the latent range. Heat moves at its real speed on the physical scale: two neighbors move the share `heatShare` of the way to their capacity-weighted mean per superstep, `PAIR_TIME / CELL_SIZE²` × the harmonic mean of their conductivities (W/m·K) × (1/Ca + 1/Cb) with the capacities in MJ/m³·K, capped at 1 (never past the mean, so heat is conserved and any conductivity is stable). Heat capacity is per cell (one cell is one unit of matter whatever its state), so a gas row's capacity is its specific heat times its liquid's density and a latent heat is per kilogram times the denser phase's density.
- Air: empty space is air on its own grid of `airCellSize`² cells (`AirGrid`, `src/air-grid.ts`; one `vec4f` per air cell: the speed through its right and top faces, pressure, temperature; one extra column and row of ghost cells beyond the edge). Units are grid cells and dispatches, so the air cell size changes detail, not speeds. The air is a linear wave (the velocity and pressure passes update in place, each reading only the other's words) with the heat carried in flux form; velocity and pressure are never advected (advecting the velocity while the pressure stays put has no energy bound and ran away near the top speed). Every air step ends with the state in the buffer it started in, so no parity is kept in JS. The world's edge is open air at room temperature; a wall drawn along it seals it. Per frame: the mask pass (face openness from `kind`, after the brush), the exchange pass, the Wind tool's pass when the pointer moved; per superstep after the flyers, `airSubsteps(s)` air steps. With `air: false` no buffer is allocated, no pass recorded and the CA and flight shaders are generated without air code.
- The exchange pass is the second writer of `temp`, and it owns the cells of its air cell (a solid trades with the air cell of its first open neighbor, so each cell belongs to exactly one thread): it runs once per frame before the CA, never inside it, and folds the frame's supersteps into one exchange, each trading the share `airShare` (`src/air.ts`, from `AIR.surfaceCoefficient`, the same for every material). Heat C·T of cells and air is conserved; a powder or liquid moving at `AIR.stillSpeed` or faster trades none, as a flyer. A new writer of `temp` outside the CA must keep one owner per cell.
- The CA reads the air (`airAround`, once per block that holds a powder, liquid, gas or fire cell, at the block's center, and the pressure for phase 8) and adds bursts to the burst buffer with an integer `atomicAdd` in fixed point: the air state is written only by the air passes, between dispatches, so the out-of-block read cannot race, and integer sums commute, so reruns stay bit-identical. `tests/block-locality.test.ts` binds a random air state. The sampled pressure gradient is 0 on the world's edge faces, as in the velocity pass. A burst (`Transition.burst`) is the pressure for a 4×4 air cell and is scaled by `(4 / s)²`.
- The Margolus offset alternates 0 then 1; never run two steps with the same offset in a row.
- The phases of one CA dispatch run in this order: 0–3 movement (0 gas buoyancy, 1 velocity, convection, repose and viscous sliding, 2 gas dispersion, 3 liquid spreading), 4 lifetimes (ignition decided), 5 element rules, 6 ignition applied, 7 heat conduction, 8 phase changes (the temperature thresholds, then the pressure transitions; left out of the shader when the table has no transition, or only pressure ones and the sim has no air). A rule never sees a cell that ignites or changes phase in the same dispatch. A cell's temperature (`cellTemp`) is its stored temperature clamped to its element's thresholds; only phase 8 compares the stored one against the thresholds. `docs/simulation.md` describes each phase.
- A frame is one `GPUCommandEncoder` and one `submit()`: `simulate()` records the brush pass, the air's mask, wind and exchange passes, all CA steps and the air steps, then `main.ts` records the render. Each CA dispatch has its own `{ offset, seed }` slot in one uniform buffer (stride `minUniformBufferOffsetAlignment`, selected by dynamic offset, written once per frame). Never submit mid-frame, and never `writeBuffer` a shared uniform between dispatches: all writes land before the first dispatch runs.
- A liquid cell's `life` field holds its sideways direction (0 none, 1 left, 2 right), not a lifetime; only the liquid spread rule reads it (`spreadRow` in `ca.wgsl.ts`). The `spread` word (a chance, 1 for anything with no viscosity) gates every sideways move of a liquid cell that its velocity does not carry; the turn-around draw happens only on a move that would be made, so a thick liquid keeps a mean free path of 64 cells.
- The brush runs once per frame, before the CA steps, along the segment from the previous frame's position.
- Block randomness comes from `pcg()` chained on `hash2(blockX, blockY, seed)`; never use a float `fract`-based hash for it.

## Adding an element

1. Add a row to `ELEMENTS` in `src/elements.ts`: the next unused ID, a `key` (generates `ELEMENT.<KEY>` and `EL_<KEY>`), label, color, `state` and `density` (kg/m³). That alone makes it fall, pile, sink or rise as its state and density say. A powder or liquid also takes `gravity` (cells per dispatch squared, default 1/32) and `drag` (share of its speed relative to the air that it loses per dispatch, in the grid and in flight, default 1/64). `flammable: true` makes it ignite beside fire; `life: { start, decay, becomes }` gives it a lifetime (the brush starts the cell at `start`); `temperature` (°C, default 20) is what the brush paints it at. The physical properties are in SI-based units, from data with the source cited in the row's comment, and each reaches the simulation through a mechanic and a test, never as unused data: `conductivity` (W/m·K, default 0; above 0, or a transition, makes it hold heat) and `heatCapacity` (MJ/m³·K per cell, above 0, default 1); `below` / `above` (`{ temp, becomes, latent }`, latent in MJ/m³ per cell: latent heat per kilogram times the denser phase's density) make it change element at a temperature, taking in or giving out its `latent` heat first (a pair that turns into each other shares one threshold and one latent heat > 0; a latent range may reach past `ABSOLUTE_ZERO` or `MAX_TEMP`); an `above` also takes a `burst` (≥ 0: the pressure added to its air cell when the cell passes the threshold, or ignites by fire if it becomes FIRE). A liquid takes `viscosity` (Pa·s; optional in the type, but the default table gives every liquid one and a test checks it; a liquid without one spreads at the cap) and may take `densityKnots` (up to four `[°C, kg/m³]` points, linear between and flat outside, so a body of it convects); a gas takes `densityTemp` (the temperature its `density` is given at, default 20 °C; the ideal-gas law does the rest); a powder takes `repose` (degrees, 20 to 45; without one it piles at 45°). A solid that crushes under pressure takes `toughness` (MPa·√m) and `pressureAbove: { becomes }`: the pressure that crushes it is toughness × `PRESSURE_PER_TOUGHNESS`, a hand-given pressure is rejected, and the chain must not lead back to the row. `validateElements` rejects out-of-range values, and a property of the wrong state (a viscosity on a powder), with an error naming the row (`tests/elements.test.ts`). An element models a real material with physical properties (say in the row's comment where each value comes from and which are tuned or estimated); one that mimics no real material says so in its row, and a generic stand-in is marked as a placeholder (WALL, SMOKE). `toolbar: n` makes it paintable, placed by n among the other buttons (the n-th button is selected by number key n).
2. Behavior the table cannot say goes in a rule: `src/shaders/rules/<name>.wgsl.ts` with `fn rule_<name>(i: u32, block: ptr<function, array<Cell, 4>>)`, registered in `src/shaders/rules/index.ts`, and `rule: '<name>'` on the row. It runs for cells of that element and reads and writes only the four cells of its block.
3. A color that depends on the cell (fire's life) is a function in `src/shaders/graphics.wgsl.ts`, named by `graphics: '<name>'`. How the finished look draws it (grain, how much of the wall behind it shows, a liquid's tint by depth) is the optional `look`, with defaults by state (`src/display-table.ts`, `docs/rendering.md`); set it where the default is wrong (a see-through solid, an opaque liquid).
4. Add a scene test of its main behavior (`tests/element-table.test.ts` shows how to run a table with an extra row), and update the density order and the phase list in `docs/simulation.md`.

## Real-world scenarios

A scenario is a real experiment the game should reproduce, written as a test whose target is computed from physical data, not from the game's own output, so a later change shows whether the game got more or less realistic. Most other scene tests guard against change with bars measured from the game. The scenes are in `src/scenarios.ts`, the helper in `tests/scenario.ts`, the tests in `tests/scenarios-heat.test.ts`, `tests/scenarios-flow.test.ts` and `tests/scenarios-todo.test.ts`; the tests of `sealedBars` (`tests/physics.test.ts`), `coolingBlock` (`tests/air-heat.test.ts`) and `heatedPot` (`tests/convection.test.ts`) build from the scenes, while `freezingPond` and `sandPile` keep their setups in their own test files (`tests/convection.test.ts`, `tests/repose.test.ts`; the `physics` lab shows both).

- **One experiment**: a scene registered in `SCENES` (so `?scene=<name>` opens it), a run of supersteps, one measurement and a target with a tolerance. The scene's name is the scenario's ID in test titles, plans and backlog lines.
- **Described in the menu**: its `SCENARIO_INFO` entry is one line (at most 110 characters, one sentence) saying what to watch, with the target only when it fits; it changes with the test's target, in the same commit. The target, the waiting time and the waiting state are shown by the in-scene readout (backlog I33). A scenario whose test waits for an item has `waitsFor` (the IDs) in its entry; its tests read it (`waitsFor()` in `tests/scenario.ts`), so the test titles and the menu agree.
- **Measured as a player sees it**: a height, a position, a temperature the readout would show, a count of cells, a time; never an internal value such as a stored latent offset. The test then needs only the elements, and stays valid whichever design passes it.
- **A fast and a full version** when the full experiment is slow: the fast one isolates one rule, the full one chains several, so when the full one fails the fast one tells which link broke. A minute of game time is 14,400 supersteps.
- **Sealed when the air is not part of it**: a heat balance runs in a box of WALL (which holds no heat) filled so that no empty cell trades heat with the air, or with `air: false`.
- **What it leaves out** is stated in the test: a real effect the game leaves out on purpose either shifts the target or stays outside the scenario's claim.

States:

| State | In the suite | Means |
| --- | --- | --- |
| Passes | a normal test | A failure is a regression |
| Waits for an item | `test.fails`, titled `<name> [waits for <ID>]: <outcome>` | Vitest passes it while it fails and fails it once it passes, so the suite stays green and the item that makes it pass also turns it into a normal test |
| Not built | `test.todo`, titled with its target | Not picked yet, or its elements do not exist |
| Out of reach | no test | A decision or a limit rules it out; the scenario is named beside it so nobody keeps trying |

- `test.fails` also passes when the test crashes, so each waiting scenario has a normal companion test: the scene loads and the measurement is a finite number in a stated range. Both attach the measured value and the target to the report (`context.annotate`), so progress shows without opening the code.
- The item a waiting scenario names is a roadmap or backlog ID. A mechanic without one that a waiting scenario needs gets a backlog line when the scenario is built.
- The GPU suites skip themselves without an adapter, so these tests run on a machine with a GPU only, never in CI (backlog D11).

Rules:

- The target is a calculation from cited physical data, written in the test with its sources, never a value the game produced.
- The tolerance is fixed before the mechanic exists, from the spread of the data (the range between sources, or the row's own cited range) and of the measurement (several seeds). Only the user changes a scenario's target or tolerance, and the plan logs it; agents keep re-measuring the regression bars of other tests as before.
- Each scenario has a control: the same scene on a test table with one property deliberately wrong (ice with half its latent heat) must miss the target. A scenario that cannot fail proves nothing.
- A constant fitted to pass one scenario is checked by another scenario, of a different size or material, that it was not fitted on (held-out checks, below).
- A scenario that starts passing before its item, through another change, is promoted in that change's commit, which also deletes its `waitsFor`, and the item's plan notes it.
- Every physical property of the element table and every physical mechanic has a built scenario, passing or waiting on a named item, or is named out of reach with its reason; a mechanic with no real counterpart (Life rules, portals) needs none. A plan that adds a physical property or mechanic writes its scenario, with a target from data, before the mechanic. Roadmap M12.13 brings what exists today to this and adds the test that enforces it.

Held-out checks:

| Constant | Fitted on | Checked by |
| --- | --- | --- |
| `CONVECTION_GAIN` | a 4×4 block of water at 90 °C in a 20 °C tank (`heatedPot`) | `heatedLayer`: other depths, and differences of 1 and 2 °C instead of 70 |
| `REF_DEPTH` | lava creeping visibly with oil slower than water | `viscousSpread` |
| `REPOSE_FIT` | piles poured from a brush 3 cells wide (`sandPile`) | the lower pile of `hourglass`, poured by a wider stream |
| `AIR.surfaceCoefficient` | the 50-cell steel block (`coolingBlock`) | `coolingBlock` at a second size: real natural convection grows as a body shrinks, the game's coefficient does not (inferred) |

## Working with the user

The user is an experienced web developer, not a physics, numerics or GPU specialist.

- Plans and docs may use precise technical terms. Anything addressed to the user (a decision request, a gate report's summary, a "needs your testing" list, a final report) says in plain words what changes for them in the game: how it looks, feels, how fast it runs, what they can do. It names the mechanism only after that, if at all.
- Ask the user only decisions with a visible or usable effect. Technical choices without one (constants, solver settings, data layouts, which algorithm passes the tests) are the agent's to make: decide, record the reason in the plan or `docs/decisions.md`, and say in one line what was chosen.
- When a decision does need the user, show it: a `?scene=` to open, a before and after, what to look for. Never ask them to pick between parameter values.
- A sub-agent's decision requests are rewritten this way before they reach the user.

## Never

- Never translate The Powder Toy's source code or copy its element tables: it is GPLv3 (`docs/decisions.md`).
- Never claim a water or physics behavior works from a visual check alone. Water realism failed repeatedly that way; any physics change needs a measurable, repeatable check, such as a scene test with a numeric threshold.
- Never judge a physics behavior through the finished look: it blurs, shades and shifts what the cells hold. Use cell data or the cells look (C), and the heat and air views for temperature and pressure.
- Never tune a constant without confirming that the value actually reaches a rule that moves particles.
